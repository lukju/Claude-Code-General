Governance ab der ersten App

Ein Entwickler sagt: «Meine App braucht X.» Nach dieser Lektion weisst du, ob die Default-Governance X erlaubt, und falls nicht, welchen Hebel ein Admin wo umlegen muss.

Dein Gewinn heute: Du kennst die Default Environment Group mit ihren fünf Hebeln und ihren Standardwerten und ordnest konkrete Anforderungen dem richtigen Hebel zu.

Aufwärmen aus Lektion 2

(8 + 2) × 0.1 = 1 Credit, also 1 US-Cent.

Das Modell: zwei Behälter

  • Personal Environment: Jeder Maker landet beim ersten Bauen automatisch in einem eigenen, isolierten Environment. Diese Routing-Regel ist permanent: Man kann sie weder abschalten noch löschen.[1]
  • Default Environment Group: Sie enthält die Regeln, die jede App erbt. Microsoft verwaltet sie, ihr Geltungsbereich ist «Everyone», löschen lässt sie sich nicht. Sie entsteht mit der ersten App oder wenn ein Admin die CMR-Verwaltung zum ersten Mal öffnet.[1]

Microsoft nennt die Defaults «restrictive on day one». Wer eine von Microsoft verwaltete Regel editiert, bekommt dafür keine automatischen Updates von Microsoft mehr. Ob man das rückgängig machen kann, sagt die Doku nicht.[1]

Was der Host ohnehin erzwingt

  • Sandbox: Der App-Code läuft in einem sandboxed iframe. Die Tokens des Hosts sind für den App-Code nicht erreichbar.[2]
  • Connector-Calls laufen über SDK und Host. Dort werden Anmeldung und Governance zentral angewendet. Für Connectors brauchst du deshalb keinen CSP-Eintrag. Den braucht nur, wer direkt aus dem Browser eine fremde Adresse aufruft.[2]
  • Zwei Schlüssel zum Öffnen: Wer eine App nutzen will, muss in der Sicherheitsgruppe des Environments sein und Zugriff auf die App haben. Teilen umgeht die Sicherheitsgruppe nicht.[2]
  • Aufsicht: Im Inventar können Admins eine App blockieren. Nutzer kommen dann nicht mehr hinein, App und Daten bleiben erhalten. Audit-Events landen in Purview unter dem Record Type CopilotManagedRuntime.[3]

Offen: Die Architektur-Seite nennt Conditional Access und DLP als Laufzeitschutz des Hosts, die Sicherheitsseiten beschreiben beides aber nicht. Auch die Admin-Pfade unterscheiden sich zwischen den Seiten (Apps › Settings › Environment groups gegenüber Settings › App settings). Im Portal prüfen.

Offene Frage · nicht abschliessend geklärt

Werden Apps für mehr Rechte «hochgestuft»?

Mögliches Konzept (Annahme): Die Default Group bleibt restriktiv, auch für die Personal Environments. Braucht eine App mehr, zieht sie in ein gemeinsames Environment mit lockererer Environment Group. Das Personal Environment des Makers wird nicht gelockert, die Ausnahme hängt an der App und ihrem Ziel-Environment.

Belegt: Makers können per ms app create --environment-id ein anderes Environment wählen, Microsoft erwähnt «shared environments».[4] Nicht belegt: dass Microsoft das als Governance-Muster empfiehlt. Technisch ist es kein Verschieben, sondern eine neue App mit neuer ID und URL. Einen Move-Befehl gibt es nicht.

Fälle zuordnen

Für jeden Fall: Was muss ein Admin tun? Kommt mehr als ein Hebel in Frage, ist der gesucht, der das Problem direkt löst.

1. Die App ruft per fetch() direkt aus dem Browser eine öffentliche Wetter-API auf. Der Aufruf scheitert.

Direkte Browser-Requests erlaubt der Default-CSP nur zur eigenen Origin (connect-src 'self'). Der Admin trägt die Wetter-API in connect-src ein. Wildcards sollte man dabei vermeiden.

2. Die App soll über den SharePoint-Connector Einträge einer Liste lesen.

SharePoint gehört zu den 19 Standard-Connectors. Der Call läuft über SDK und Host, also ist auch kein CSP-Eintrag nötig.

3. Die App nutzt im SharePoint-Connector die Aktion «Send an HTTP request to SharePoint».

Der Connector ist erlaubt, offene HTTP-Aktionen sind aber standardmässig gesperrt. Der Admin muss die Aktion in den Advanced Connector Policies freigeben. Danach bekommt diese Regel keine automatischen Updates von Microsoft mehr.

4. Ein externer Partner mit Gastkonto im Tenant soll die App nutzen.

Teilen mit Gästen ist standardmässig aus. Achtung: Ist die Gastfreigabe an, umfasst «Organization-only» auch Gäste.

5. Ein Entwickler will aus VS Code mit ms app deploy deployen. Schon das Erstellen der App scheitert.

Im Power Platform Admin Center unter Copilot › Settings › Managed apps die Einstellung «Allow app creation with the Copilot Managed Runtime command line interface (CLI)» für die Environment Group oder das Environment aktivieren.

6. Eine Person hat die App geteilt bekommen und ist lizenziert, kann sie aber trotzdem nicht öffnen. Wahrscheinlichster Grund?

Es braucht beides: Mitgliedschaft in der Sicherheitsgruppe des Environments und Zugriff auf die App. Teilen allein reicht nicht.

7. Die Security entdeckt eine problematische App. Sie soll sofort gestoppt werden, ohne Daten zu verlieren.

Blockieren im Inventar sperrt die Nutzer aus und behält App und Daten. Die Default Group und die Routing-Regel lassen sich gar nicht löschen bzw. abschalten.

8. Was ist der Preis, wenn man eine von Microsoft verwaltete Regel editiert?

Die Regel gehört dann dir. Neue Connectors oder Anpassungen, die Microsoft einführt, kommen nicht mehr automatisch an.

Abruf-Übung

Zähl die fünf Hebel der Default Environment Group auf, jeweils mit ihrem Standardwert. Nicht hochscrollen.

  • Connectors/MCP (ACP): 19 Microsoft-Connectors, 12 MCP-Server, kein Drittanbieter
  • Gesperrte Aktionen: HTTP, Run script, unbound/bound action
  • Sharing: Organisation an, Gäste aus, privat bis geteilt
  • CSP: durchgesetzt, nur eigene Origin
  • CLI-Erstellung und externe Artefakte: aus
