Copilot Managed Runtime · Lektion 4 · ca. 15 Minuten (plus 20 Minuten Praxis mit Tenant)

Erste App mit der CLI

Git und npm kennst du. Neu ist, wie CMR aus deinen Commits eine laufende App macht: in drei Stufen, und jede Stufe hat ihren eigenen Befehl.

Dein Gewinn heute: Du kennst die drei Stufen Local, Preview und Live, weisst, welcher Befehl wohin führt und was einen Build auslöst, und kannst eine Live-Version zurückrollen.

Aufwärmen aus Lektion 3

Ein Entwickler will ms app create ausführen, und der Befehl scheitert. Was muss ein Admin wo einschalten? Kurz überlegen, dann aufdecken.

Die Einstellung «Allow app creation with the Copilot Managed Runtime command line interface (CLI)» im Power Platform Admin Center unter Copilot › Settings › Managed apps, für die Environment Group oder das Environment. Standardmässig ist sie aus.[1]

Die drei Stufen

1 · Local

ms app dev startet einen Webserver auf deinem Rechner. Die URL läuft trotzdem über den gehosteten Player (play.managedapps.cloud.microsoft), dadurch funktionieren Entra-Login und Connectors schon lokal. Kein Build, kein Deploy.

2 · Preview

Jeder gepushte Commit ist abspielbar. ms app play --mode preview baut den neuesten Commit bei Bedarf. Die URLs enthalten Commit oder Branch: …/commit/<SHA> bzw. …/branch/<name>.

3 · Live

ms app deploy macht einen Build zur Live-Version. Die Live-URL bleibt über alle Deploys gleich. Weitere Pushes ändern sie erst beim nächsten Deploy. Zu Beginn sehen sie nur die Owner.

Quelle: Build, preview, and deploy apps.

Fünf Regeln, die anders sind als gewohnt

  • Ein Push baut nicht. Gebaut wird erst bei Preview, Deploy oder ms app build.[2]
  • Ein fehlgeschlagener Build ändert nichts. Die Preview zeigt weiter den letzten erfolgreichen Build, mit dem Hinweis «Latest build failed». Das Log liefert ms app build-status --show-log.[3]
  • Zurückrollen heisst einen alten Commit deployen: ms app deploy --commit <SHA>. In der Versionskontrolle geht nichts verloren.[4]
  • Nur was gepusht ist, wird deployt. Mit uncommitteten oder ungepushten Änderungen fragt ms app deploy nach (im JSON-Modus bricht der Befehl ab). Auch --force lädt keine lokalen Änderungen hoch.[3]
  • Den Repo-Modus wählst du nur einmal: plattformverwaltet (Standard), eigenes GitHub-Enterprise-Cloud-Repo (--repo <url>, muss leer sein) oder eigener Build (--repo none, ohne Preview). Ein Wechsel geht nur über eine neue App.[4]

Reihenfolge üben

Bring die Schritte vom leeren Rechner bis zur geteilten App in die richtige Reihenfolge. Mit den Pfeilen verschiebst du einen Schritt.

  1. git add . && git commit && git push
  2. ms app deploy
  3. ms auth login
  4. ms app add data-source --connector …
  5. ms app share <personen>
  6. ms app create hello-world --display-name "Hello World"
  7. ms app play --mode preview
  8. npm install && ms app dev

Anmelden, App anlegen (Plattform-App, Repo und Projektdateien), lokal entwickeln, Connector hinzufügen (erzeugt typisierte Models und Services in generated/), pushen, Preview bauen und prüfen, live schalten, teilen. Der Connector kann auch erst später kommen. Wichtig ist, dass Push vor Preview und Preview vor Deploy steht.

Prüfe dich

1. Du hast eben auf main gepusht. Was passiert automatisch?

Ein Push allein löst keinen Build aus. Gebaut wird erst bei ms app play --mode preview, ms app build oder ms app deploy.

2. Der neueste Build ist fehlgeschlagen. Was zeigt die Preview?

Die Preview zeigt den letzten erfolgreichen Build mit dem Hinweis «Latest build failed. Showing the last successful build.» Eine «never deployed»-Seite erscheint nur, wenn es noch nie einen erfolgreichen Build gab.

3. Die Live-Version ist kaputt. Wie rollst du zurück?

Mit git log den letzten guten Commit suchen und ihn deployen. ms app build baut nur, und ein git revert mit Push ändert die Live-Version ebenfalls nicht, solange niemand deployt.

4. Du hast schon ein Vite-Projekt und willst es an CMR anbinden, ohne neu anzufangen.

ms app init registriert ein bestehendes Webprojekt. ms app create braucht einen leeren Ordner, clone holt ein bestehendes Plattform-Repo und pack baut nur lokal.

5. ms app dev läuft, aber Chrome blockiert den Zugriff der gehosteten Seite auf localhost.

Seit Dezember 2025 blockieren Chrome und Edge standardmässig den Zugriff öffentlicher Seiten auf localhost. Nötig ist eine Browser-Berechtigung oder eine Enterprise-Policy. Mit der CSP der App hat das nichts zu tun.

6. Wo landet das Ergebnis von ms app add data-source?

Die CLI registriert den Connector in ms.config.json und erzeugt typisierte Models und Services in generated/. Dein Code importiert aus generated/. Nach Schemaänderungen: ms app refresh data-source.

Praxis, wenn du einen Tenant hast

Voraussetzungen:

  • Node.js ab v24.11.0, Git ab v2.27.0 mit Git Credential Manager.[5]
  • Die CLI-Erstellung ist für dein Environment freigegeben (Lektion 3).
  • Für das lokale Ausführen brauchst du Power Apps Premium oder eine Spending Policy mit CMR (Lektion 2). Ohne Credits wird man laut SDK-Übersicht nach 20 App-Operationen oder fünf Minuten blockiert.[5]
  • Öffne die URLs im Browserprofil deines Tenants.
npm install -g @microsoft/cmr-cli
ms --version
ms auth login
ms app create hello-world --display-name "Hello World"
cd hello-world
npm install
ms app dev                      # Local-Play-URL öffnen
ms connector list --only-allowed
git add . && git commit -m "first pass" && git push
ms app play --mode preview
ms app deploy                   # gibt die Live-URL aus

Beobachtungsauftrag: Schau nach ms app create in ms.config.json und notiere, welches Environment dort steht. Das knüpft an die offene Frage aus Lektion 3 an. Schick mir die Ausgabe von ms connector list --only-allowed und von ms app create --help, dann prüfen wir sie zusammen.

Die SDK-Übersicht zeigt keinen Beispielcode zur Laufzeit-API. Wie die Services in generated/ aussehen, schauen wir an, sobald du sie erzeugt hast.

Abruf-Übung

Nenn die drei Stufen, den Befehl, der jeweils dorthin führt, und sag, was eine Preview-URL von der Live-URL unterscheidet.

Local: ms app dev. Preview: pushen, dann ms app play --mode preview. Live: ms app deploy. Preview-URLs enthalten Commit oder Branch. Die Live-URL hat keinen Bezeichner und bleibt über alle Deploys gleich.
